# Шаг 3.5. Авторизация менеджера (Техническое задание)

Этот документ описывает требования и архитектуру системы авторизации для кабинета менеджера (админ-панели). Все изменения должны быть реализованы без внешних npm-пакетов, используя только стандартную библиотеку Node.js.

## 1. Функциональные требования

### 1.1. Проверка конфигурации пароля
* Пароль администратора задается в переменной `ADMIN_PASSWORD` в файле `.env`.
* Если переменная `ADMIN_PASSWORD` не задана, пуста или состоит только из пробелов, вход в панель администратора должен быть полностью заблокирован.
* При попытке входа в заблокированном состоянии API должно возвращать ошибку с понятным описанием (например: `"Вход заблокирован: на сервере не задан пароль администратора"`).

### 1.2. Сессии и куки (HttpOnly Cookie-сессия)
* Авторизация работает на сессиях, хранящихся в оперативной памяти сервера (Memory Session Store). Нет необходимости использовать базу данных для хранения сессий.
* При успешном вводе пароля сервер генерирует криптографически стойкий идентификатор сессии (Session ID) с помощью `crypto.randomUUID()` или `crypto.randomBytes()`.
* Сессия сохраняется в серверной коллекции (например, `Map` или простой объект) со следующими полями:
  * `id`: строка (Session ID)
  * `createdAt`: метка времени создания сессии
* Сервер отправляет Session ID клиенту в заголовке `Set-Cookie` с параметрами безопасности:
  * `HttpOnly` — обязательно (защита от кражи куки через JS/XSS).
  * `Path=/` — доступно для всех путей сайта.
  * `SameSite=Lax` — защита от CSRF при стандартных переходах.
  * `Max-Age` или `Expires` — сессия должна быть активна, например, в течение 7 дней (или быть сессионной кукой, удаляемой при закрытии браузера, по выбору).
* При выходе из кабинета (запрос `POST /api/admin/logout`):
  1. Сессия удаляется из памяти сервера.
  2. На клиент отправляется заголовок `Set-Cookie` с обнулением куки (например, `Max-Age=0` или прошедшей датой).

### 1.3. Ограничение попыток входа (Rate Limiting)
* Для защиты от брутфорса (перебора паролей) вводится ограничение попыток входа с одного IP-адреса.
* Логика ограничений:
  * Максимум 5 неудачных попыток входа в течение 15 минут.
  * При превышении лимита IP временно блокируется на сервере на 15 минут.
  * При заблокированном IP сервер сразу отвечает статусом `429 Too Many Requests` с сообщением о блокировке и оставшимся временем ожидания.
* IP-адрес клиента определяется с учетом настройки `TRUST_PROXY` из `.env`:
  * Если `TRUST_PROXY` равен `true`, IP извлекается как первый адрес из заголовка `X-Forwarded-For`.
  * Если `TRUST_PROXY` равен `false` или не задан, IP берется из `req.socket.remoteAddress`.

### 1.4. Защита страниц и API-маршрутов
* **Маршрут `/admin` (Кабинет менеджера):**
  * Если кука сессии отсутствует или недействительна: сервер перенаправляет пользователя (`302 Found`) на `/admin/login`.
  * Если сессия валидна: отдается статический файл личного кабинета (в будущем `public/admin/index.html`).
* **Маршрут `/admin/login` (Страница входа):**
  * Если сессия валидна: сервер перенаправляет пользователя (`302 Found`) на `/admin`.
  * Если сессии нет: отдается статический файл страницы входа `public/admin/login.html`.
* **API-маршруты `/api/admin/*`:**
  * Все будущие и текущие API для панели управления (получение списка заявок, смена статуса, просмотр защищенных фото) должны проверять наличие активной сессии.
  * При отсутствии валидной сессии возвращается статус `401 Unauthorized` в формате JSON: `{"ok": false, "error": "Необходима авторизация"}`.

## 2. Архитектура и файлы

Будут созданы и изменены следующие файлы:

1. **`server/auth.js`** — новый модуль для управления авторизацией, сессиями и защитой от перебора.
   * Экспортирует функции:
     * `checkSession(req)` — проверяет куку сессии и возвращает `true/false` (или объект сессии).
     * `login(password, clientIp)` — проверяет пароль, увеличивает счетчик попыток, создает сессию и возвращает `{ success, sessionId, error, status }`.
     * `logout(sessionId)` — инвалидирует сессию.
     * `isIpBlocked(clientIp)` — проверяет, не заблокирован ли IP-адрес.
2. **`server/index.js`** — интеграция модуля авторизации:
   * Импорт `server/auth.js`.
   * Перехват роутов `/admin` и `/admin/login` для выполнения редиректов и отдачи нужных HTML-файлов.
   * Обработка API-запросов `POST /api/admin/login` и `POST /api/admin/logout`.
   * (Опционально на этом шаге) Создание базового защищенного API-маршрута проверки статуса `/api/admin/status`.
3. **`public/admin/login.html`** — новая адаптивная страница входа.
   * Форма ввода пароля.
   * Загрузка настроек `config.json` для стилизации страницы в цветах бренда (переменные `--primary` и `--accent`).
   * Кнопка «Войти» с анимацией загрузки.
   * Вывод ошибок валидации и блокировки IP-адреса.

## 3. Алгоритм ручного парсинга Cookies на чистом Node.js
Поскольку внешние библиотеки использовать нельзя, парсинг Cookie реализуется вручную:
```javascript
function parseCookies(req) {
    const list = {};
    const cookieHeader = req.headers.cookie;
    if (!cookieHeader) return list;

    cookieHeader.split(';').forEach(cookie => {
        let [name, ...rest] = cookie.split('=');
        name = name.trim();
        if (!name) return;
        const value = rest.join('=').trim();
        list[name] = decodeURIComponent(value);
    });
    return list;
}
```

## 4. Критерии приемки Шага 3.5

1. При попытке зайти на `/admin` без авторизации происходит автоматический редирект на `/admin/login`.
2. На `/admin/login` отображается стильная форма входа, оформленная в цветах из `config.json`.
3. Если ввести неверный пароль 5 раз подряд, IP блокируется на 15 минут, и выводится сообщение об ограничении попыток.
4. При пустом или отсутствующем `ADMIN_PASSWORD` в `.env` вход заблокирован сразу.
5. При вводе правильного пароля устанавливается HttpOnly кука, и пользователь перенаправляется на `/admin`.
6. Находясь на `/admin/login` с живой сессией, пользователь автоматически перенаправляется в кабинет `/admin`.
7. Все запросы к `/api/admin/*` без сессии возвращают `401 Unauthorized` с JSON-ответом.
